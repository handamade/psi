# Psi 0.22 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the five gaps the VEGA.OTA portal found in Psi 0.21 (D90–D94) and release them as 0.22.0. Tier 2 (the later portal needs) is deferred to 0.23.

**Architecture:** One decision, one branch, one PR, merged serially in dependency order, then one `release/psi-0.22.0` PR. Every decision gets a spec with a `## Decisions` entry, failing tests first, a `minor` changeset, and the five gates.

**Tech Stack:** React 19 components with CSS Modules, a token build (`packages/tokens`), an MCP server (`packages/mcp`), vitest + axe (jsdom), Playwright (`vr`, `test:site`), changesets, pnpm 11 on Node 24.

Source brief: `~/Projects/dku/psi-handoffs/2026-10-07-psi-0.22-portal-handoff.md` (called "the handoff" below). Written 2026-10-08 against `main` `1919655`. **Status: for review. Nothing in this plan has been executed. No branch, commit or PR exists.**

## Global Constraints

- Node 24 (`.nvmrc`): check `node -v` before the first pnpm command; fix a stale shell with `nvm use`, never with a per-command PATH override.
- Sizes are px numbers; variants are flat; no hardcoded colours in component CSS (stylelint plugin); new token values go in `packages/tokens/src`, never in `dist`.
- `--psi-space-*` binds gap, padding and margin only, never `height` (`psi/token-scopes`). `psi/component-tokens-only` admits a component's own prefix plus the scale families. Token prefixes are kebab-case.
- **Every default stays unchanged** unless the spec argues the change is a fix (only D90 and D94 may change what every consumer gets).
- Gates, in this order, on every PR: `pnpm build && node tools/check-docs-drift.mjs && pnpm test && pnpm lint && pnpm --dir apps/promo build && pnpm test:site`. `vr` runs only in CI, allows **0** differing pixels (D89), and baselines come from CI's `vr-baselines` artifact, never from a macOS run.
- Do not run `pnpm test:e2e --grep <story word>` (writes `-darwin` junk baselines); grep `@interaction` titles or run the full `pnpm test:e2e`.
- Every user-visible change carries a `minor` changeset (lockstep at one number). `git commit --amend` and force-push are denied: use follow-up commits.
- Arm auto-merge at PR creation and read it back with `gh pr view <n> --json autoMergeRequest`; if null, use the `enablePullRequestAutoMerge` GraphQL mutation. The `protect-main` ruleset is strict, so merge serially: a second open PR goes stale and costs a ~5.5 min `ci` re-run.
- Re-check the D-number at PR time as well as spec time (decision-numbers-collide-late).
- Branch names (no Linear issue): `d90-announcement-region`, `d91-toast-announce-queue`, `d92-filter-form-error-line`, `d93-tabs-navitem-consumer-state`, `d94-utilities-win`.
- Before every pnpm command that depends on `dist`, make sure it exists (`pnpm build` first); `test:site` must run from the repo root.

### 1.2 Where the handoff is wrong or incomplete

1. **D90's "red today on `aria-prohibited-attr`" does not reproduce in jsdom.** `a11y.axe.test.tsx:88` already renders `<ToastRegion><Toast variant="success">…</Toast></ToastRegion>` and passes (`vitest run src/a11y.axe.test.tsx -t "Toast in a region"` → green). Either axe files this under `incomplete` rather than `violations`, or jsdom hides the popover. The `role="region"` unit test is red regardless, but the axe test the handoff calls red is not. Task 2 begins by finding out which, in a real browser, before it claims a red axe test.
2. **D92 option (b) is not "simpler".** With `align="end"` and a reserved message line in each `Field`, a `Field`'s bottom edge is the reserved line, while *Find* (no label, no message) has its bottom at its own control. *Find* then sits one message line (16 px + the field gap) **below** the controls. (b) therefore needs the same offset token as (a), plus a permanent blank line. That settles D92 in favour of (a) (see 2.3).
3. **D92's offset needs more than "a token".** The offset is the label's line height (`--psi-text-14-20-medium` is a `font` shorthand, so there is no line-height variable to read) plus `--psi-field-gap`. `--psi-space-*` cannot carry a label height. The plan adds one Field-owned token and derives the offset from it, so the two cannot drift (Task 4).
4. **D94 names only half the risk.** The handoff warns that a consumer whose CSS sits in a *layer* now beats Psi where it lost before. The larger exposure is the reverse: once component CSS is layered, any *unlayered* consumer rule beats it **regardless of specificity**. A consumer reset such as `button { padding: 0; font: inherit }` or `* { margin: 0 }` previously lost to `.psi-button` on specificity and now wins. Storybook's and the promo site's global CSS are consumers of this kind. D94's spec must state both directions and its VR step must treat any diff as a defect to explain.
5. **The D61 spec text is stale.** `2026-08-05-overview-allocation-design.md` says the floor holds through 21 and breaks at 22. The measurement script, run today, says: realistic ids hold through **23**, break at **24**; short ids hold through 24, break at 25. The handoff's "holds through 23, breaks at 24" is correct and matches the D88 spec; the D61 spec's own table is the stale part, and the budget decision (2.2) must refresh it.
6. **"Tier 2 needs up to five new patterns" overstates the base case.** D95, D96 and D97 change existing components and need no pattern. Only D98 (`Textarea`, `RadioGroup`) and D99 (`ProgressBar`, `Disclosure`, `FileUpload`) add components, so patterns added is 0–5. One pattern that demands both D98 components is legal (the rule is that a pattern demands the component, not one pattern per component).
7. **A.3's "Toolbar fixes each control's width" is narrower than stated.** `toolbar.module.css` fixes width only for direct `> input` and `> select` children. A `Field`-wrapped control is not width-fixed. The conclusion (no slot for a button beside an `Input`) still stands; the reasoning in the portal's A.3 note should not be reused unqualified.

### 2.2 The D61 pattern-budget question (decide before tier 2; not needed for tier 1)

**Facts (measured today, `measure-overview-envelope.ts`):** 22 patterns; the eight-component floor holds through 23 and breaks at 24 (realistic ids). Tier 1 adds **no** pattern (D92 changes `filter-form`). So 0.22 is unaffected and has one pattern of headroom.

**Options for tier 2, with what each costs:**

| Option | Effect | Cost |
| --- | --- | --- |
| A. Raise `RESPONSE_BUDGET` 6000 → ~8000 | Largest headroom | Contradicts D61's "not up for negotiation", the D43 agent-access docs and the "stays within the response budget" test; every agent that calls `search("")` pays ~500 more tokens, forever |
| B. Lower `COMPONENT_FLOOR` 8 → 5 | ~+3 patterns | Weakens the third guarantee; 46 components, so the overview shows a smaller sample |
| C. **Shrink the irreducible per-pattern cost in the overview projection** | Probably +4–6 patterns | Changes the overview row shape for patterns |
| D. Do nothing; add at most one pattern | Holds at 23 | Blocks D99 and any second D98 pattern |

**Recommendation: C, as its own decision, written and merged before any tier-2 pattern, and not in 0.22.** D61's spec says the failure mode must be "summaries get terser", and the irreducible cost is the id stored twice (`id: "pattern:<id>"` and `title: "<id>"`), `kind`, and the never-capped gaps tail. `overviewBrief()` already builds a pattern-only projection (`store.ts`), so dropping the redundant `title` from pattern rows in the *overview only* (stored briefs and `score()` are untouched) removes ~25 bytes per pattern at the real average id length (13.4 chars), about a fifth of the irreducible cost. That is my estimate, not a measurement. **The first step of that decision is to measure it**, with the existing script, and the acceptance criterion is: the floor of 8 holds through **at least 27** patterns (22 + the five tier 2 could add) with realistic ids. If C cannot reach 27, fall back to C + B (floor 6) before considering A.

Risks to put in that spec: the overview row shape changes for patterns (anything reading `title` from an overview row breaks; check `packages/mcp/src/server.ts`, the `init`-generated AGENTS.md and the hosted MCP's clients); and refresh the stale 21/22 table and the "treat 21 as the planning number" paragraph in the D61 spec.

Number: claim it with the first free `## Decisions` entry when that branch starts (D95 if nothing else has taken it); the tier-2 component numbers shift by one. Do not pre-assign.

### 2.3 D92: recommend option (a), with the corrections in 1.2

**(a) Align on the controls; messages hang below.** Reasons, in order of weight:

1. (b) needs the same offset token as (a) (finding 2), so it saves nothing and adds a permanent blank line.
2. (a) lifts today's restriction: `Toolbar`'s own doc says a `Field` in an end-aligned row must have "no description or error line". Under (a) a description or error hangs below and shifts no other control.
3. It keeps `align="end"` (default `center` unchanged) for every existing consumer.

Costs to state in the spec: every label in the row must be one line, or the controls fall off the shared line silently (the handoff's B.6 risk, kept); and the offset is coupled to `Field`'s label metrics, which is why one Field token feeds both (Task 4). I do not recommend trying to hide this with `align-items: baseline`: a `Select` and an `Input` do not share a baseline, and the button text differs.

**Resolved design details for the spec:** `Toolbar` `align` gains `"start"` (additive; `center` stays default, `end` unchanged). `filter-form` moves from `align="end"` to `align="start"`. Under `start`, unlabelled actions (`> button`, `> a`) take `margin-block-start: var(--psi-toolbar-action-offset)`. The `filter-form` pattern's `intent` says the error line is the `Field`'s own, with its usual `aria-describedby` wiring, and that labels must be one line.

## Task 3: D91 — one queue for toasts and announcements

**Branch:** `d91-toast-announce-queue` (after D90 merges). **Size:** M.

**Files:** Modify `Toast/ToastProvider.tsx` (queue, `show`, region props), `Toast/useToast.ts` (context type), `Toast/Announcement.tsx` (doc comment), `ToastProvider.test.tsx`; stories; docs. Create the spec.

**Interfaces:**
- Consumes: D90's `role="region"` and non-atomic wrappers.
- Produces, on the `useToast()` value: `announce(message: ReactNode, options?: { politeness?: ToastPoliteness }): string` (returns an id), beside `show`, `dismiss`, `clear`. `ToastProvider` also accepts `Omit<HTMLAttributes<HTMLDivElement>, "children">`-style region props (`aria-label`, `ref`, `data-*`, `className`) which it forwards to `ToastRegion`.

**Resolved design (settle in the spec; these are my recommendations):**

- **Dwell:** 1000 ms, a named constant `ANNOUNCEMENT_DWELL = 1000`. Rationale to document: long enough for a screen reader to start speaking an added node, short enough that the live wrapper does not accumulate stale text. It is what the portal runs today.
- **Lifetime rule:** each announcement leaves **after** its dwell. I recommend **not** removing an announcement early when a later one of the same politeness arrives (the handoff says "replaces it"). An early removal can cut speech in some screen readers; with `aria-atomic="false"` a second added node speaks on its own. If the spec adopts "replace", it needs a measured reason.
- **Never counts against the visible-toast `limit`:** keep two arrays or a `kind` tag; the eviction loop at `ToastProvider.tsx:105` counts toasts only.
- **Skip the optional queue hook** (YAGNI): a hand-composed `ToastRegion` is what `announce()` makes unnecessary. State this in the spec so it is a decision, not an omission.
- **Docs:** `Announcement` replaces "Remove it once it has been spoken" with the lifetime rule, and still says it belongs inside the one region and renders no live region.
- **Keep one region and one queue** (B.6): `announce()` renders an `Announcement` into the existing wrappers; it never renders a live region.
