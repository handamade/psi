# A public visually-hidden utility, and the three private copies it replaces (D80)

Date: 2026-08-10. Status: **Draft**.

Provenance: flagged mid-implementation of the D78–D79 eval-gaps cycle. That
cycle's `data-table` task originally asked for a visually-hidden table header;
the implementer refused to build it and reported the gap instead — Psi has no
public way to visually hide content, the technique exists only as private CSS
duplicated across three component modules, and nothing in `llms.txt` documents
the convention. Recorded then as a follow-up worth its own decision; this is
that decision.

## What's there today

`Toast/toast.module.css`, `Checkbox/checkbox.module.css` and
`Switch/switch.module.css` each define a byte-identical block (Toast's is
literally commented `/* Same recipe as checkbox.module.css /
switch.module.css. */`):

```css
position: absolute;
width: 1px;
height: 1px;
padding: 0;
margin: -1px;
overflow: hidden;
clip: rect(0, 0, 0, 0);
white-space: nowrap;
border: 0;
```

Toast's copy (`.srOnly`) hides a standalone status-prefix `<span>`. Checkbox's
and Switch's (`.input`) hide the native `<input>` itself — the element stays
focusable and operable; only its box is removed from view while a custom
sibling renders the visible control. Same technique, two different jobs, three
copies, and no public class a consumer could reach for a fourth.

**The recipe is also incomplete.** `better-accessibility`'s canonical `.sr-only`
pattern carries both `clip: rect(0 0 0 0)` *and* `clip-path: inset(50%)` —
`clip` is deprecated (still universally supported, but `clip-path` is its
non-deprecated modern equivalent) and shipping both costs nothing. None of the
three existing copies has `clip-path`. Canonizing this into a public,
long-lived utility is the moment to carry the complete recipe rather than
propagate the gap a fourth time.

## Decisions

- **D80 — `.psi-sr-only` ships as a utility, generated by the same mechanism
  D79 built, and the three private copies migrate onto it.**

  **Mechanism: no new codegen path.** `.psi-container` and `.psi-media-tint`
  are the existing precedent for a hand-added, multi-property, unscaled
  utility family — added by hand to both `emitUtilitiesCSS()` and
  `emitUtilitiesRoster()` in `packages/tokens/scripts/emit-utilities.ts`,
  same as every other utility D79 made machine-readable. `.psi-sr-only` is a
  third instance of that same shape:

  ```css
  .psi-sr-only {
    position: absolute;
    width: 1px;
    height: 1px;
    padding: 0;
    margin: -1px;
    overflow: hidden;
    clip: rect(0 0 0 0);
    clip-path: inset(50%);
    white-space: nowrap;
    border: 0;
  }
  ```

  `emitUtilitiesRoster()` gets a matching `UtilityFamily` entry (`prefix:
  "psi-sr-only"`, `scale: null`, `classes: ["psi-sr-only"]`), so it appears in
  `guidance.json` → `utilities.classes` the moment it's built — no separate
  wiring, per D79's "generated from the same source as the CSS" rule.

  **Documentation:** a new entry in `packages/tokens/llms.txt`, in the shape of
  the existing `## Tabular numerals` entry — names the class, states what it
  does, states the platform rule (never `display: none` / `visibility:
  hidden` for this).

  **Consumption: `className` concatenation, not CSS Modules `composes`.**
  `NavBar.tsx` already does `` `psi-container ${styles.inner}` `` — a live
  precedent for a component mixing a global tokens utility with its own scoped
  module class. `composes: psi-sr-only from global;` would reach the same
  runtime output but introduces a CSS Modules feature this codebase has never
  used; matching the existing pattern wins on YAGNI grounds.

  **The three migrations:**

  - **Toast** (`Toast.tsx`, `toast.module.css`): `.srOnly` has no combinator
    use anywhere in the file, so the ruleset is deleted outright.
    `className={styles.srOnly}` becomes `className="psi-sr-only"` — no module
    class needed at all for this element any more.

  - **Checkbox** (`Checkbox.tsx`, `checkbox.module.css`) and **Switch**
    (`Switch.tsx`, `switch.module.css`): `.input` is not just cosmetic — it's
    the sibling-selector anchor for `.input:checked + .indicator`,
    `.input:focus-visible + .indicator` (Checkbox) and `.input:checked +
    .track`, `.input:focus-visible + .track` (Switch). The bare `.input { ...
    }` ruleset's *declarations* are deleted, but the combinator rules stay
    untouched, and CSS Modules still exports a valid `styles.input` — the
    tooling scans every class-selector token in the file, not just standalone
    rulesets, so a class that appears only inside `.input:checked + .indicator`
    is still a real export. `className={styles.input}` becomes
    `` className={`psi-sr-only ${styles.input}`} ``.

  No component's rendered output, ARIA, or prop surface changes. Existing
  tests query by role/text/state, not CSS class, so none should need updating;
  new coverage is a `guidance.json` roster assertion (`utilities.classes`
  includes `psi-sr-only`), matching the pattern D79's roster test set.

  **Naming:** `psi-sr-only` follows the existing bare-utility convention
  (`psi-container`, `psi-tabular`, `psi-media-tint` — no scale suffix, no
  extra modifiers) and the industry-standard `sr-only` term the
  `better-accessibility` skill and Tailwind both use, so an agent or developer
  who already knows the term finds it on the first guess.

## Gates

All five, in order, `pnpm build` first (regenerates `guidance.json`):

```bash
pnpm build && node tools/check-docs-drift.mjs && pnpm test && pnpm lint && pnpm test:site
```

**Every test proven red before the fix**, per the standing rule from D70/D71/
D79: the roster assertion must fail against today's `guidance.json` (no
`utilities` family named `psi-sr-only` exists yet), and it's worth a second
assertion that `utilities.css` actually contains `.psi-sr-only { ... }` after
build — a roster entry with no matching CSS would be the exact "two sources of
truth" failure D79 was written to close.

A changeset is required — `.psi-sr-only` is a new public class, which is
user-visible. Following the `fixed` group in `.changeset/config.json` (all
three packages always release at the same version, bumped to the highest type
present), the entries are:

- `@handamade/psi-tokens`: **minor** — new utility class, new `guidance.json`
  family.
- `@handamade/psi-mcp`: **minor** — serves the updated roster, matching D79's
  rationale for including it.
- `@handamade/psi-react`: **patch** — internal dedup only; no prop, behavior,
  or ARIA change for any consumer.

The fixed group still resolves to a single **minor** release regardless of
this split; the split exists so each package's own `CHANGELOG.md` states its
actual change accurately (`psi-react`'s entry should read as cleanup, not
feature).

`vr` is CI's — this cycle adds no stories and changes no visual output
(`.psi-sr-only`'s whole point is that nothing becomes visible), so it should
not move.

## Out of scope

- **A focusable variant** (`sr-only-focusable`, for skip links — content
  hidden until it receives focus). No current Psi component or pattern needs
  one; Psi ships no skip link today. Speculative addition, rejected on YAGNI
  grounds. If a skip-link pattern is ever designed, it claims its own decision
  number and can build on `.psi-sr-only` rather than duplicating it.
- **Auditing other components for the same duplication.** This cycle is scoped
  to the three copies that are already known and measured. If a fourth
  surfaces later, it's a one-line migration onto the utility this decision
  ships — not a reason to widen this cycle now.
